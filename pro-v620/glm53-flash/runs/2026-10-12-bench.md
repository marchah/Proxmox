# GLM-5.3-Flash: the full benchmark batch on the best configuration

Plan committed 2026-10-12 · Status: planned

## Question

What does GLM-5.3-Flash deliver on CT 123 in the usage batch (`make bench GPU=2
MODEL=glm53f`), on the best configuration the [configurations
record](2026-10-10-configurations.md) found, at one 64k slot?

- **Regression items:** single-request baseline, the concurrency sweep, the input-length
  sweep to 32k tokens, and the soak.
- **Workloads:** the scripted agent sessions (`hermes` and `coding`, stopped at 56k on the
  one 64k slot) and document ingestion at 8k, 16k, 32k and 48k tokens.
- **Per phase:** what the card, the CPU and the DIMMs do while it runs.

The same batch ran on the same card with Flash-Next's deployed configuration (`-ncmoe 37`,
`dio`, MTP head at n-max 3, one 64k slot) in the [prefill-slowdown
record](../../qwen38-flash-next/runs/2026-10-10-prefill-slowdown.md), stage 3. Its figures
are set beside this run's for reference: same card, suite, prompt text and slot layout, a
different model.

## What answers it

- Per regression item, the suite's `REPORT.md` and `SLO.md`: prefill and decode rates per
  prompt and depth, time to first token, and request latency per concurrency point. Decode
  is quoted with its prompt class and depth, and prefill separately.
- Agent sessions: per preset, `session_wall_seconds`, the per-band prefill and decode rates
  and draft acceptance, and `cache_misses`, which should be zero with nothing else using the
  server.
- Document ingestion: per prompt size, prefill rate, time to first token, decode rate and
  draft acceptance, median of three runs, with `sections_ok` and `repeatable`.
- The target telemetry merged into each run: card power, clocks and busy % against the
  250 W cap, CPU cores in use, and the hottest DIMM, per phase.
- VRAM: a residency sampler on the card for the whole batch gives the least free VRAM and
  any VRAM-requested memory outside VRAM. Under `dio` the CPU-resident experts are about
  180 GiB of pinned GTT, so the telemetry's GTT total is not a spill reading.
- Output: the suite's degenerate-output and error counts per item. `SLO.md` checks errors,
  the DIMM limit and low RAM, the file's model-independent limits.
- A run with any DIMM sample at 66 °C is reported as capped, item by item.

## Configurations

| Standard configuration | Cells |
| --- | --- |
| One GPU | CT 123 with [`glm53f-bench.env`](../glm53f-bench.env) on `0000:83:00.0`: every routed expert in RAM (`-ncmoe 46`), `dio`, batch and micro-batch 4096, 32 threads, f16 KV, context 65536 in one slot, `--reasoning-budget 0`, MTP at n-max 2 |

Each setting and the record stage behind it:

| Setting | Value | From |
| --- | --- | --- |
| Cards | one, GPU 2 | owner, after stage 6 |
| Context | 65536 | owner, after stage 6 |
| Load mode, micro-batch | `dio`, 4096 | stage 3 |
| Threads | 32 | stage 4 |
| KV type | f16 | stage 1 |
| Reasoning budget | 0 | stage 1 |
| Placement | `-ncmoe 46` | stage 7a: MTP's only fit |
| Speculation | MTP, n-max 2 | stages 7b–7c: all four MTP criteria held |
| Slots | one 64k slot | owner, for this batch (2026-10-12) |

- **One slot is not what the configurations record measured.** Its stages ran two 32k slots.
  The owner chose one 64k slot, Flash-Next's layout on this card. One slot holds every item:
  input to 32k, ingestion to 48k and sessions to 56k. Two 32k slots hold none of these.
  - MTP at n-max 2 at `-ncmoe 46` with one slot is a combination never measured together.
    The fit check below covers it before the batch runs.
  - With one slot, concurrency points above 1 queue behind it, so two-stream decode is not
    exercised. The configurations record's stage 7c measured it.
- **Two GPUs:** left out; the owner chose one card after stage 6.
- **CPU only:** left out. `make bench` measures the server a GPU's container runs, and the
  configurations record measured CPU only (stage 4).
- **Optimized:** the configuration already holds every routed expert in RAM, which leaves
  the card about 10 GiB free.
- **Speculative decoding:** on, as above. The configurations record measured MTP against its
  no-speculation control (stage 7c), so this batch runs no control.

**Install and restore.** GLM is not deployed. `ct123-test-host.sh one-card` stops and
disables Flash-Next, gives CT 123 240 GiB and 48 cores, and points the thermal watchdog's
map for GPU 2 at `llamacpp-glm53f`. `install.sh` with `glm53f-bench.env` writes the
configuration as `/etc/llamacpp-glm53f.env`. After the batch, `ct123-test-host.sh restore`
puts Flash-Next back and restores CT 123's limits and the watchdog map.

## Controls

None. Flash-Next's batch is a reference for the same card and suite, not a control: the
model differs.

## Method

Code at this branch's head when the run starts: `make bench` stops on uncommitted benchmark
code and records the commit in each run's `versions.json`, with `capture-env.sh`'s capture.
The host-side scripts run from the same commit, staged with `push-harness.sh`.

```bash
# Host, as root
H=/root/harness/<sha12>/pro-v620
cd $H/glm53-flash
./ct123-test-host.sh one-card
VMID=123 ENV_FILE=glm53f-bench.env ./install.sh
pct exec 123 -- systemctl start llamacpp-glm53f       # dio load, about 2 min
systemd-run --unit=vram-residency --collect /usr/bin/python3 \
  $H/qwen38-flash-next/vram-residency-sampler.py --pci 0000:83:00.0 \
  --output /root/glm53-flash/residency-bench.jsonl

# Mac, from the repo root of this worktree
make bench GPU=2 MODEL=glm53f SECRETS=<main checkout>/ansible/secrets.yml

# Host, after the batch
cd $H/glm53-flash && ./ct123-test-host.sh restore
systemctl stop vram-residency
```

- **Fit check, before the batch:** one chat request of about 5.8k tokens to the loaded
  server, with the residency sampler running.
  - It passes on the configurations record's rule: at least 3,072 MiB free (provisional) and
    nothing outside VRAM.
  - If it fails, the batch does not run, and the record says so.
- **The batch:**
  - It checks that CT 123 serves `llamacpp-glm53f` and has `llamacpp-glm53f-reload`, starts
    CT 200 and captures the environment.
  - Before each item it reloads CT 123 at 65536 and one slot, and it wraps each item with
    `run-with-target-telemetry.sh`.
  - Afterwards it restores CT 123 at one slot, fetches the results and shuts CT 200 down.
- **Items, in order:**
  1. `llm-bench-baseline`;
  2. `llm-bench-sweep concurrency --points 1 2 4 8 16 --requests 32`;
  3. `llm-bench-sweep input-length --points 128 512 2048 8192 32768 --output-tokens 32`;
  4. `llm-bench-soak`;
  5. the workloads profile with `BENCHMARK_AGENT_DEPTH=56000`.

  Repetitions are the suite's own (three runs per workload preset and prompt size).
- **After `restore`:** Flash-Next must load and answer with about 3.2 GiB free and nothing
  outside VRAM, as after the configurations record.
- **Expected duration: about 5–7 h.**
  - The configurations record measured decode of about 8.4 t/s and prefill of 150–170 t/s.
    The 2026-10-09 Flash-Next batch took 5 h 34 min at about 14 t/s decode and 105 t/s
    prefill.
  - A request of 512 tokens with 128 output tokens takes about 25 s. At 16 requests in
    flight, the last waits about 400 s, inside the client's 600 s timeout.
- **Raw data:** `pro-v620/results/llamacpp-gpu2-glm53f/parallel-1/<run>/` on the Mac
  (gitignored), one folder per item, and `/root/glm53-flash/residency-bench.jsonl` on the
  host.

## Safety

- **Guests:** CT 123 and CT 200 run for the batch; the playbook starts CT 200 and shuts it
  down at the end.
  - CT 120 `llamacpp`, CT 121 `hermes`, CT 140 `kb-rag`, CT 201 and VM 300 `docker-host`
    stay shut down. Starting any of them again waits for the owner's go-ahead.
  - CT 120, 121 and 140 and VM 300 have `onboot=1`, so a host reboot would start them; none
    is planned.
- **Cards:** CT 123 holds only `0000:83:00.0`, and CT 120 holds only `0000:03:00.0` and is
  stopped.
- **Thermal:** `gpu-thermal-watchdog` maps `0000:83:00.0` to `123:llamacpp-glm53f` while
  `one-card` is in place. It stops that unit at 102 °C junction or 101 °C memory, and the
  batch's server runs under it.
- **DIMMs:** no guard during the batch. The BMC's fan curve is at 100% from 58 °C, and the
  telemetry records the hottest DIMM for each item. The configurations record peaked at
  58–59 °C in its MTP cells and at 63 °C in CPU only.
- **Job timeout:** amdgpu's compute job timeout is 10 s. The batch's deepest request, 48k
  tokens, is below the ~65k tokens past which the 2 s default failed.
- **Images:** the batch sends no image requests, which fail with MTP on (#30204).
- **Timing:** keep clear of the Sunday 01:00 backup window. CT 121's 04:00 ET cron does not
  run, since CT 121 is off.

## Environment

Intended: llama.cpp b11505 (release tarball), Mesa 26.2.4 (kisak-mesa), kernel
`7.0.14-22-pve`, `schedutil`, 8 × 64 GB DDR4-3200, amdgpu compute job timeout 10 s. CT 123
with 48 cores and 240 GiB holding `0000:83:00.0` at 0 mV and 250 W. Replaced by the batch's
`capture-env.sh` capture when the run starts.
