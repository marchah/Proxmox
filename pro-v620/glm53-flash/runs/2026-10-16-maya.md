# GLM-5.3-Flash: Project Maya in place of llama.cpp

Plan committed 2026-10-16 · Run 2026-10-16 · Status: running

## Question

How fast does [Project Maya](https://github.com/mw00/project-maya) v1.1.15 serve
GLM-5.3-Flash on GPU 2 (CT 123, one V620, `0000:83:00.0`), and on both cards, against the
best llama.cpp configuration measured here, with correct output? How much more does Maya's
own quant, Maya-L, give?

This is a first speed reading, as the Strata record was for Flash-Next. It is not a search for
Maya's best settings. Only the configurations expected to gain the most are run: the
engine on the file llama.cpp serves, a second card, the MTP block, and one smaller quant.

**Why Maya.** It is the only engine built for this model that runs on AMD cards. Candidates
checked on 2026-10-16:

| Project | Why it is in or out |
| --- | --- |
| **Project Maya** (`mw00/project-maya`, MIT) | In. A GLM-5.3-Flash engine that started from Strata's and was rewritten for this model. Builds through HIP; RDNA2 (`gfx1030`, V620) is accepted as experimental since v1.1.12 and compiles since v1.1.13 ([#205](https://github.com/mw00/project-maya/issues/205)). No one has reported a run on an RDNA2 card yet. Reads Unsloth GGUFs: UD-Q4_K_XL ran on v1.1.11 on an EPYC 7532 and ROMED8-2T with 512 GB of DDR4, with NVIDIA cards ([#218](https://github.com/mw00/project-maya/issues/218)) |
| PolyStrata (`VecSzn/PolyStrata`) | Out: its GLM engine supports NVIDIA only ("Not yet: AMD cards") |
| `sybil-solutions/glm-flash-lite` and `glm53-flash-offload` | Out: EXL3 on CUDA |
| KTransformers | Out: its GLM-5.3-Flash path runs the FP8 checkpoint through SGLang, and its guides use NVIDIA cards. RDNA2 has no FP8 arithmetic |
| WARP (`sqliteai/warp`) | Out: for models larger than RAM, streams experts from NVMe; CPU and Metal backends only. This model fits in RAM here |
| vLLM, SGLang and the EXL3 recipes | Out: CUDA, with the whole model in VRAM |

**What Maya does differently** from llama.cpp's `-ncmoe 45`:
- It splits the experts across three tiers: VRAM, pinned RAM and the SSD. The VRAM tier
  follows the conversation (least recently used, with one request).
- A CPU lane computes RAM-tier experts while the GPU works. A start-up timing splits each
  token's RAM-tier experts between the CPU and copies over PCIe.
- It reads prompts in chunks of up to 32,768 tokens on one card, copying each routed expert
  to VRAM once per chunk.
- It keeps each attention layer's KV in pinned RAM and a window of it in VRAM.
- On two cards it splits the layers, and the second card runs the model's MTP block. The
  two halves then work on consecutive tokens. On one card the MTP decode is off by default
  except on Ryzen AI Max APUs, and `STRATA_GLM_MTP_DECODE=1` turns it on: it drafts up to
  three tokens a round and picks the length by measured speed. The docs warn it is usually
  slower where experts stream from RAM.

**Measurements elsewhere** (Maya's README and issues; this run does not reproduce them):
- RX 7900 XT (gfx1100) alone: about 15 t/s decode. With an R9700 as well, about 33 t/s
  (drafts about 76% accepted). Prompt speed 414 against 490 t/s at 4K. Maya-S, 8K context,
  v1.0.11 ([AMD guide](https://github.com/mw00/project-maya/blob/v1.1.15/docs/AMD_MAYA.md#two-gpus)).
- R9700 alone, Maya-S: 19.7–21.4 t/s decode, v1.1.12
  ([#213](https://github.com/mw00/project-maya/issues/213)).
- RTX 3090 with an EPYC 7702P (eight DDR4 channels), Maya-M at 128K: 27.0 t/s decode and
  1,069 t/s prefill at 8K, v1.1.4. The same box with an RTX 3060 added: 33.7 t/s.

RDNA2 has no matrix cores. Maya therefore runs its portable kernels there, including the
F32 prompt attention kernel. hipBLASLt ships no gfx1030 kernels, so the dense prompt GEMMs
use plain hipBLAS.

**The llama.cpp configuration** is the long-tasks record's winner, `glm53f-long.env`:
- b11583, `-ncmoe 45`, micro-batch 2048, `GGML_OP_OFFLOAD_MIN_BATCH=512`;
- MTP at n-max 2 and p-min 0.2;
- 32 threads pinned one per physical core, at one 64k slot.

It decoded 9.64 t/s at d0 and 8.71 at d8000, and read the d8000 prompt at about 142 t/s
([long-tasks record](2026-10-13-long-tasks.md), stages 2 and 4). GLM-5.3-Flash is not
deployed.

## What answers it

**Gate (stage 1).** A file and arm pass the gate only if all of these hold, and no speed
result counts before that:
- **Next-token agreement with llama.cpp on the same file.** The text is one sequence of
  4,096 tokens: the first 512 of each of eight of this repository's READMEs. The reference is
  llama.cpp b11583 on the CPU, decoding it one token at a time (Maya's
  `tools/llm_logits_dump.cpp`), kept as the top 64 log-probs at each of the 4,031 positions
  after the first 64 tokens. Maya scores the same positions through its one-token decode
  path on GPU 2 (`STRATA_GLM_SCORE` with `STRATA_GLM_SCORE_TOPK`). Thresholds:
  - mean KL below 0.10;
  - the same top token at 90% of positions or more;
  - perplexity within 3% of llama.cpp's on the same positions.

  On scale: Strata's HIP and CUDA builds on one file differed by KL 0.038 (94.5% same top
  token). Maya's docs put the CPU lane's own arithmetic at about 0.06. Maya-L against FP8,
  a whole quantization step, is 0.188. A broken kernel shows far above these figures, as
  Strata's [#2457](https://github.com/Niko1221/Strata/issues/2457) did (IQ3_S garbage on RX 6000
  cards). Maya-L's gate/up experts are IQ3_S.
- **Chat contract**, on every arm: a bare chat and efforts `none`, `low`, `high` and `max`
  all return a non-empty reply, with no `<think>` tag in `content`.
- **Tool calls**, on every arm: a parsable call to the declared tool with JSON arguments,
  both streamed and not.
- **Probe rows:** none empty, degenerate (the probe's 8-gram gate) or cut off without
  tokens. A cold row must read its whole prompt: the engine log's `prompt N tokens = R
  reused + F read` line shows R = 0.
- **Engine log:** no watchdog, stall or non-finite line in any cell.

**Arms (stage 2).** Each arm keeps one configuration for stage 3:
- One-card arm: the faster of `1c` and `1c-mtp` by median decode, provided no depth's cold
  prefill falls more than 10%.
- Two-card arm: `2c`, unless `2c-nospec` decodes faster.
- Maya-L runs in stage 3 on whichever arm decodes faster.

Stage 2 runs one pass per cell, so a difference under 3% between two cells is reported as a
tie. The tie goes to the cell with fewer non-default settings. `1c` runs first and last; the
difference between its two loads bounds the drift.

**Maya against llama.cpp (stage 3).** `llamacpp`, `maya-1c`, `maya-2c` and `maya-l`, in
three interleaved rounds. For each measure, the result is the ratio of medians. It counts
as a difference only beyond both cells' pass-to-pass spreads. The measures:
- decode per prompt class at d0, d8000 and d32000;
- cold prefill and time to first token at each depth;
- draft acceptance where a cell drafts.

The record reports these as measurements. Deploying GLM, using GPU 1 for it and
switching file are the owner's decisions.

A cell with any DIMM sample at 66 °C is reported as capped and not used for a decision.

## Configurations

**Model files:**
- **UD-Q4_K_XL**, the six shards llama.cpp serves (`/models/hf/glm-5.3-flash/`, Unsloth
  revision `a38483c8`). This isolates the engine. Maya runs Unsloth files as "experimental:
  they run, but Maya is not measured with them" (docs/SETUP.md). Its routed experts are
  Q4_K gate/up and Q5_K down, K-quants like the Flash-Next file Strata ran correctly on this
  card.
- **Maya-L**, 156.3 GB (`peasantsmith/GLM-5.3-Flash-Maya-GGUF`, revision `f16ee4ba`, folder
  `Maya-L/`, SHA-256s from `maya.py` at v1.1.15). Of Maya's four quants, it is the closest to
  FP8: KL 0.188, the same top token as FP8 at 90.0% of positions, 99.2% of FP8's zero-shot
  accuracy (bench/results/MAYA-L.md). The file is 22% smaller than UD-Q4_K_XL. Its routed
  experts are IQ3_S gate/up, with IQ4_XS down (Q5_K in the first and last four MoE layers).
  The gate also reports Maya-L's KL against the UD-Q4_K_XL reference, which shows what the
  smaller file costs against the file in use. Maya-M (116 GB) and Maya-S (96.5 GB) give up
  more accuracy and are not run.

**Maya pack:** Maya's setup writes a pack, an index of about 1 GB, into the model's folder.
`--gguf-dir` points at a folder of symlinks to the shards (`/models/maya/ud-q4_k_xl/`), so
the pack stays out of llama.cpp's folder. If the pack builder does not follow symlinks, the
pack goes beside the shards; stage 0 reports which.

**Starting configuration.** The setup's choices for this box come from
`maya.py --backend hip --context 65536 --no-vision --yes --no-start`: the reserve, the
prompt budget, `--prefill auto`, KV streaming and the shipped expert profile. Two changes
are made to them:
- `STRATA_GLM_RAM_RESIDENT=1`: the RAM tier holds every expert the VRAM does not, so
  nothing is read from the SSD while it answers. The start fails if it cannot.
- `STRATA_GLM_NO_REUSE=1`: no prompt reuse (the snapshot of the last prompt, the SSD slots
  and the checkpoints), so each probe row reads its whole prompt.

The other settings: thinking off, as llama.cpp's `--reasoning-budget 0` does; 64k
context, llama.cpp's one 64k slot; one request at a time. The CPU lane takes one thread per
physical core, which is 32 on CT 123's CPU set `0-47`.

| 1. Gate | UD-Q4_K_XL and Maya-L, each on GPU 2 with the starting configuration: agreement with llama.cpp, the contract, tool calls. `2c` with UD-Q4_K_XL: the contract and tool calls | Whether Maya computes this model correctly on RDNA2 |

| 3. Against llama.cpp | `llamacpp` (`glm53f-long.env`, GPU 2); `maya-1c` and `maya-2c` (stage 2's arms); `maya-l` (Maya-L on the faster arm) | Engine, cards and file |

All cells run in CT 123 holding both cards. A one-card cell names GPU 2 by its PCI address:
`HIP_VISIBLE_DEVICES` for Maya, `MODEL_VK_VISIBLE_DEVICES` for llama.cpp. The two-card
cells put GPU 2 first, the order of Strata's best two-card cell (`split21`, within 0.3% of
the other order). The engine's split search picks the split point.

Standard configurations:
- **One GPU:** every stage. This is the question.
- **Two GPUs:** stages 2 and 3. Maya's MTP decode is built around two cards, the halves
  working on consecutive tokens. llama.cpp gained nothing from a second card on this model
  (+1.4% decode, [configurations record](2026-10-10-configurations.md), stage 6), so its
  control runs on one card. GPU 1 otherwise serves CT 120 and Hermes; CT 120 stays stopped
  throughout.
- **CPU only:** left out. Maya needs a GPU, and llama.cpp's CPU-only figure is in the
  configurations record (4.9 t/s decode).
- **Optimized, leaving resources free:** left out. GPU 2 holds one model, and the expert
  pool takes the VRAM left over.

**Drafters:**
- The MTP block is measured against a no-drafter control on each arm: `1c-mtp` against `1c`,
  `2c` against `2c-nospec`. Acceptance is quoted from the engine's `glm spec:` line.
- On one card the MTP decode drafts up to `STRATA_GLM_MTP_DRAFT` tokens (default 3). Each
  round it picks the length with the most tokens per second it has measured
  (`STRATA_GLM_MTP_ADAPT`), so `1c-mtp` scans lengths 0–3 itself. llama.cpp peaked at
  n-max 2 on this model and fell at 3. Two cards draft one token ahead, the halves on
  consecutive tokens; there is no length to set.
- DFlash2 is left out: Maya runs it on NVIDIA RTX 30 / A100 and newer only. llama.cpp's
  DFlash2 path aborts on this model (#30093).
- Two concurrent streams are left out. The llama.cpp configuration under comparison serves
  one 64k slot, and Maya's single-card MTP decode does not run with `--parallel`.

**Left out as unlikely to gain much here:**
- Maya's `--calibrate`: it kept nothing on 3× V100, and the R9700 report found the
  defaults best. The start-up timing already splits the CPU lane against PCIe, and
  re-times it in decode.
- `--kv-streaming off`, `STRATA_GLM_KV_INT8` and the prefetch settings.
- `STRATA_GLM_VRAM_EVICT=least`: `lru` is the default.
- The settings that change answers (`TRUNK_KEEP`, `MISS_SKIP`, `DISK_SKIP`).
- The experimental expert helper.

## Method

**Stage 0 builds the tooling, committed before stage 1:**
- `pro-v620/maya/`, the counterpart of `pro-v620/strata/`:
  - `install.sh` checks Strata's ROCm 10.0 userspace in CT 123 (`/opt/rocm/core-10.0`). It
    clones Maya v1.1.15 (`a4e1ff0`) to `/opt/maya/maya-v1.1.15` with its pinned llama.cpp
    (`3cf0325`), and builds `build/strata` and the AMD guide's test targets for gfx1030 as
    `maya.py` does.
  - It builds llama.cpp b11583 for the CPU and Maya's `tools/llm_logits_dump.cpp` against it.
    The dumper's copy takes `DUMP_THREADS` (32); the original runs llama.cpp's default 4 threads.
  - It writes the packs: `/models/maya/ud-q4_k_xl/` links llama.cpp's six shards, and
    `/models/maya/Maya-L/` holds Maya-L (`maya-l-download.sh`).
  - It installs `maya-glm53f.env`, the launcher `maya-serve-glm53f` and the `maya-glm53f`
    unit, with `Conflicts=` on the four other model units and `LimitMEMLOCK=infinity`. The
    launcher writes Maya's JSON config from the env file at every start and resolves PCI
    addresses to HIP indices.
- `glm53-flash/ct123-test-host.sh` takes `TEST_ENGINE=maya`:
  - It passes `/dev/kfd` through, and keeps the DRM cgroup rule to the bound cards' minors at
    every card change, as `use-engine.sh strata` does.
  - It retires Strata as well as llama.cpp's Flash-Next unit. `restore` enables the one that
    was enabled before the test.
  - `engine` moves the watchdog's map to the other GLM engine without a restart.
- `strata/strata-sweep.sh` takes `UNIT=maya-glm53f`, with `../maya/maya-glm53f.env` as its base
  env and GLM's efforts. `strata-cell.py` reads Maya's log: the `glm fast:` lines (expert
  pool and RAM tier), the `glm stat:` lines (VRAM hits, RAM fetches, CPU-lane experts, disk
  reads) and the `glm spec:` lines. `strata-summary.py` prints a Maya table, and
  `capture-env.sh` records Maya's release, build and config.
- `maya/maya-gate.sh` and `maya-gate.py` run the gate: tokens, reference, score, verdict.
- `maya/maya-vs-llamacpp.sh` runs stage 3's rounds, as `strata-vs-llamacpp.sh` does.

Stage 0 also checks:
- `tools/test_maya_hip.py` and the AMD guide's ctest subset on GPU 2;
- the start-up lines for VRAM and the RAM tier;
- that the probes parse Maya's `timings`;
- that thinking stays off;
- that a repeated cold row reads its whole prompt.

If llama.cpp b11583 does not load Maya-L, Maya-L's gate falls back to Maya with every
expert on the CPU lane as the reference. That isolates the card's IQ3_S and IQ4_XS expert
kernels, as Strata's yardstick did.

**Run:** from `/root/harness/<sha12>/pro-v620/` (`./push-harness.sh`):

```bash
cd glm53-flash && TEST_CPUSET=0-47 TEST_ENGINE=maya ./ct123-test-host.sh two-card
VMID=123 UNIT=maya-glm53f PATTERNS="build/strata llama-server llm_logits_dump" \
  ../qwen38-flash-next/thermal-guard.sh                                  # separate shell
# a residency sampler per card: --comm strata, and --comm llama-server on GPU 2 for stage 3
cd ../maya && ./maya-gate.sh                                              # stage 1, UD-Q4_K_XL
LABEL=maya-l PACK=/models/maya/Maya-L/pack ALSO_REF=ud \
  MODEL=/models/maya/Maya-L/GLM-5.3-Flash-Maya-L-IQ3_S-00001-of-00004.gguf ./maya-gate.sh
cd ../strata && UNIT=maya-glm53f PASSES=1 \
  CELLS=../glm53-flash/runs/2026-10-16-maya-2-arms.cells ./strata-sweep.sh   # stage 2
cd ../maya && ./maya-vs-llamacpp.sh                                       # stage 3, 3 rounds
```

- Chat mode, greedy, 256 tokens, prompt classes `code`, `list` and `prose` at depths 0, 8000
  and 32000. The summary prints the measured sizes.
- One warm-up request per load is left out of the results.
- The gate's contract and tool calls come from the sweep's probes: stage 2's first loads of
  `1c` and `2c` count for UD-Q4_K_XL, and stage 3's for Maya-L.
- Stage 3's Maya cell file, `2026-10-16-maya-3-maya.cells`, is written from stage 2's arms and
  committed before stage 3 runs. `2026-10-16-maya-3-llamacpp.cells` holds the control.
- Duration: stage 0 is about 2 hours, dominated by the build and the 156 GB download at
  about 66 MB/s. The gate's llama.cpp reference decodes 4,096 tokens on the CPU, about 15
  minutes per file. Stage 2 is five loaded cells. Stage 3 is three rounds of one llama.cpp
  cell, roughly 20 minutes at its d32000 prefill, and three Maya cells. The record adds the
  measured times once a load has been measured.
- Raw data lands in `/root/glm53-flash/` on the host, in `maya-gate-*`, `maya-sweep-*` and
  `maya-vs-llamacpp-*` directories.

## Safety

- Every other guest stays shut down. On 2026-10-16 the following are already stopped:
  CT 120 `llamacpp`, CT 121 `hermes`, CT 140 `kb-rag`, CT 200 `bench-runner`, CT 201
  `llamacpp-builder` and VM 300 `docker-host`. They wait for the owner to restart them.
- CT 123 serves Flash-Next through Strata on GPU 2, as the owner left it on 2026-10-16. The
  run takes CT 123 over with `ct123-test-host.sh two-card`, which gives it both cards, 240
  GiB and 48 cores, and turns CT 120's autostart off.
- At the end, `ct123-test-host.sh restore` returns CT 123 to the Flash-Next engine enabled
  before the test, Strata on GPU 2, with CT 120 stopped and `onboot=1`.
- `thermal-guard.sh` watches both cards in every stage, beside the watchdog. A trip stops
  the stage, and cooling is checked before anything restarts.
- **Memory:**
  - The RAM tier is pinned: about 160 GiB for UD-Q4_K_XL's experts outside VRAM, and less
    for Maya-L.
  - It fits CT 123's 240 GiB and the 251.8 GiB GTT limit.
  - Stage 0 records the pinned size. A start that cannot pin the tier fails under
    `RAM_RESIDENT`; it does not fall back to the SSD.
- **Disk:**
  - Maya-L adds 156.3 GB to the model store. Stage 0 checks the space with `df -h
    /mnt/models/store` before the download.
  - The build tree (`/opt/maya`) is rebuildable bulk on CT 123's root disk, like
    `/opt/strata`.
- If stage 1 fails on UD-Q4_K_XL, the campaign stops there, and the record reports the gate's
  numbers. Whether to file them upstream on #205 is the owner's decision.

Run 2026-10-16 20:25–20:55 ET, harnesses `0b54496` to `b053133`.

  Two install attempts failed in pip and in `git ls-remote`, and the third ran through. The
  Maya-L download stalled at 44 GB and resumed by itself.
- The pack builder prints that it drops the MTP block's 26 tensors (`blk.45`). That message

  the prompt path's MMQ parity, which needed its target built.

  card has no WMMA. On gfx1030 the engine takes the F32 kernel whatever is asked

starting configuration on GPU 2):

- VRAM before the expert pool: 9.66 of 29.98 GB (dense weights 8.62, 64k state 0.66). The
  expert pool held 17.32 GB, 1,213 slots (28–42 per layer), and 3,106 MiB stayed free.
- The RAM tier pinned 172.96 GB in 12,107 slots, and the engine verified every expert in
  VRAM or pinned RAM.
- The CPU lane took 32 threads, at 0.147 ms per expert against 0.545 ms over PCIe. Of a
  route's 0–8 RAM-tier experts, the CPU computes 0, 1, 2, 3, 3, 4, 5, 6 and 7.
- Prompt chunks of 2,048 tokens, borrowing 4,081 MB of the pool while a prompt runs.
- `capture-env.sh` recorded the release, commit, engine SHA-256, ROCm package, HIP runtime and
  the six shards with their stamps.

**Smoke requests**, greedy:
- The answers were correct: 17 × 23 = 391; 91 = 7 × 13.
- Thinking stayed off by default. Effort `low` reasoned briefly, then answered.
- A tool call returned `get_weather` with `{"city":"Paris"}`.
- Decode ran 9–10 t/s on short prompts in the first minutes after the start.
- With slots and checkpoints off, a repeated prompt still read only 1 of its 24 tokens: the
  engine keeps a snapshot of the last prompt. `STRATA_GLM_NO_REUSE=1` replaced the two
  settings in the starting configuration (`b053133`) before any timed cell.
- The two greedy replies to that prompt differed after a few words. The experts that sit in
  VRAM, and those the CPU lane computes, change from one request to the next, and the two
  paths round differently. Maya's release notes say the same about the CPU lane.

## Deviations

Made during stage 0, before any measurement, with the plan text updated to match:
- `STRATA_GLM_NO_REUSE=1` replaced `STRATA_GLM_SLOTS=0` and `STRATA_GLM_CKPTS=0`. The plan's two
  settings left the engine's snapshot of the last prompt, which served a repeated prompt from
  it.
- The one-card MTP decode does have a draft length (`STRATA_GLM_MTP_DRAFT`, 3), which the
  engine adapts per round. The plan had said there was none to scan.
- Method names the tooling as built: the gate runs one 4,096-token sequence (eight texts ×
  512), not 8 × 1,024, because llama.cpp's reference decodes one token per call on the CPU.

Made during stage 2, after `1c`, `1c-mtp` and part of `2c-nospec`:
- **The two-card cells give the split (`MODEL_LAYER_SPLIT=24`), where the plan let the engine's
  split search place it.**
  - The search prices each card from HIP's memory clock: 2 × clock × bus width. On the V620
    it read 64 GB/s; the card's GDDR6 gives 512 GB/s. At 64 GB/s, an expert read from VRAM
    prices slower than the CPU lane computing it (67 GB/s, each part's share of the host's
    RAM read speed), so the search placed as few experts in VRAM as it could.
  - The result: layers 0–1 on GPU 2, which are dense, and 2–44 on GPU 1. GPU 2 held no
    expert pool (29,890 MiB free), so it had no prompt path, and every prompt ran token by
    token at about 110 ms per token. A d32000 row took 34 minutes.
  - The sweep was stopped during `2c-nospec`'s second d32000 row; its first seven rows are
    reported. `2c` had not run.
  - `2026-10-16-maya-2b-split.cells` runs `2c-nospec` and `2c` again at layer 24, then
    `1c-end`. Layer 24 gives each card 21 MoE layers, and the same room per MoE layer within
    2% by UD-Q4_K_XL's tensor sizes. Both cells use the same split, so they differ only in
    the MTP block.
