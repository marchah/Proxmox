# Qwen3.8-Flash-Next: the full benchmark batch with `dio` and the MTP head

Plan committed 2026-10-10 · Run 2026-10-10 · Status: done

## Question

What does CT 123 deliver in the usage batch (`make bench GPU=2`) with the best one-card
configuration found: `--load-mode dio` and the Q4_K_M MTP head at n-max 3, at
`-ncmoe 36`?

- **Regression items:** single-request baseline, the concurrency sweep, the input-length
  sweep to 32k tokens, and the soak.
- **Workloads:** the scripted agent sessions (`hermes` and `coding`, stopped at 56k on the
  one 64k slot) and document ingestion at 8k, 16k, 32k and 48k tokens.
- **Per phase:** what the card, the CPU and the DIMMs do while it runs.

The [best-configuration check](2026-10-10-best-config.md) measured this configuration only
up to ~5.8k-token prompts; the batch takes it to 48k-token prompts and a 56k context.

## What answers it

- Per regression item, the suite's `REPORT.md` and `SLO.md`: prefill and decode rates per
  prompt and depth, time to first token, and request latency per concurrency point. Decode
  is quoted with its prompt class and depth, and prefill separately.
- Agent sessions: per preset, `session_wall_seconds`, the per-band prefill and decode
  rates, draft acceptance, and `cache_misses`, which should be zero with nothing else
  using the server.
- Document ingestion: per prompt size, prefill rate, time to first token, decode rate and
  draft acceptance, median of three runs, and whether the note wrote all three sections.
- Against the [2026-10-09 batch](2026-10-09-bench.md) (the deployed configuration, same
  build, card, items and prompts): each figure above side by side, with the change. Each
  batch ran once, so differences are reported as measured, not tested against a spread;
  the suite's own repetitions give the spread within an item.
- The target telemetry merged into each run: card power, clocks and busy % against the
  250 W cap, GTT, CPU cores in use, and the hottest DIMM, per phase.
- Output: the suite's failed-request, degenerate-output and error counts per item.
- A run with any DIMM sample at 66 °C is reported as capped, item by item.

## Method

Code at the branch head when the run starts; `make bench` stops on uncommitted benchmark
code and records the commit and `capture-env.sh`'s capture, which shows the installed env
file and server command line, in each run's `versions.json`.

```bash
# Host: install the configuration for the batch
pct exec 123 -- cp -p /etc/llamacpp-qwen38fn.env /etc/llamacpp-qwen38fn.env.pre-bench-20261010
pct exec 123 -- sed -i \
  -e 's/^MODEL_CPU_MOE=.*/MODEL_CPU_MOE="36"/' \
  -e 's/^MODEL_LOAD_MODE=.*/MODEL_LOAD_MODE="dio"/' \
  -e 's|^EXTRA_ARGS=.*|EXTRA_ARGS="--device Vulkan0 --spec-type draft-mtp --model-draft /models/hf/qwen3.8-flash-next/mtp-Qwen3.8-Flash-Next-Q4_K_M.gguf --spec-draft-ngl all --spec-draft-n-max 3"|' \
  /etc/llamacpp-qwen38fn.env
pct exec 123 -- /usr/local/bin/llamacpp-qwen38fn-reload 65536 1
# Mac, repo root (the worktree has no ansible/secrets.yml)
make bench GPU=2 SECRETS=<main checkout>/ansible/secrets.yml
# Host: restore the deployed configuration
pct exec 123 -- cp -p /etc/llamacpp-qwen38fn.env.pre-bench-20261010 /etc/llamacpp-qwen38fn.env
pct exec 123 -- systemctl restart llamacpp-qwen38fn
```

- Before the batch, a request at ~5.8k tokens checks that the server loads the head
  (draft tokens in its `timings`) and that VRAM and GTT match the best-configuration
  record's `dio-mtp3` cell (1,773 MiB free at load, about 56.4 GB of GTT).
- The batch checks that CT 123 serves its model and has `llamacpp-qwen38fn-reload`, starts
  CT 200 if it is stopped, captures the environment, then reloads CT 123 before each item
  (the helper changes only the context and slot count) and wraps it with
  `run-with-target-telemetry.sh`. Afterwards it reloads CT 123 at one slot and fetches
  the results.
- Items, in order: `llm-bench-baseline`; `llm-bench-sweep concurrency --points 1 2 4 8 16
  --requests 32`; `llm-bench-sweep input-length --points 128 512 2048 8192 32768
  --output-tokens 32`; `llm-bench-soak`; the workloads profile with
  `BENCHMARK_AGENT_DEPTH=56000`. Repetitions are the suite's own.
- With one slot, concurrency points above 1 queue behind it; they measure latency under
  queueing, not parallel decode.
- Every reload under `dio` reads the CPU-resident weights cold, about 70 s.
- Expected duration: under the 2026-10-09 batch's 5 h 34 min, since prefill and decode
  are both faster at ~5.8k tokens.
- Raw data: `pro-v620/results/llamacpp-gpu2/parallel-1/<run>/` on the Mac (gitignored), one
  folder per item.

## Safety

- Every guest the batch does not use stays shut down: CT 120 `llamacpp`, CT 121
  `hermes`, CT 140 `kb-rag`, VM 300 `docker-host` and CT 201. CT 123 and CT 200 run for
  the batch. Starting any other guest again waits for the owner's go-ahead.
- `gpu-thermal-watchdog` maps `0000:83:00.0` to `123:llamacpp-qwen38fn` and stops it at
  102 °C junction or 101 °C memory; the batch's server runs under that unit. Under `dio`
  the card prefills at about 160 W (75 °C junction at ~5.8k tokens), and the batch's
  prefills run up to 48k tokens.
- The DIMMs have no guard during the batch: the BMC's fan curve is at 100% from 58 °C, and
  the telemetry records the hottest DIMM for each item.
- `dio` with the head holds about 82 GiB in CT 123, within its 120 GiB.
- The deployed env file is restored after the batch, also if the batch fails.
- Keep clear of the Sunday 01:00 backup window.

### Prefill slowdown in the workloads

From 13:41:20 to 14:51:11 UTC, prefill on 2k–9k-token prompts ran at 61–91 t/s, against
137–280 t/s before and 286–305 t/s on the documents after. Two readings changed at both
ends of that stretch, to the sample:

- **Memory placement.** Before and after, VRAM and GTT moved with every request: GTT
  between 56,545 and 57,395 MiB, VRAM between about 28,600 and 30,678 MiB. Through the
  stretch they did not move: GTT stayed at 57,569 MiB, 1,024 MiB above its usual
  56,545, and VRAM at 28,701 MiB. One earlier turn, at 13:38:30, reached the same 57,569
  MiB and prefilled at 137 t/s. VRAM had peaked at 30,678 of 30,704 MiB at 13:23.
- **Memory clock.** In prefill, the card's memory clock read its lowest level, 96 MHz, in
  66% of samples (3% outside the stretch) and 1,000 MHz in 18% (88%). In decode it read
  1,000 MHz in 97% (99%). The core clock stayed at 2,380–2,395 MHz and busy at 99%.

Through the stretch, junction temperature stayed at or below 74 °C and the hottest DIMM at
or below 59 °C, and the host logged no kernel message. The state ended during a 32k
document's prefill, without a reload.

## Conclusion

Against the criterion fixed during the run, this configuration fails one condition:
`coding`'s median session took 988 s against 848 s. Every other condition held: no request
failed, no reply was empty, no slot cache was lost, the hottest DIMM reached 59 °C and the
watchdog never stopped the server. `hermes`' median session was shorter (768 s against
1,179 s), every ingestion size finished sooner (by 53–62%), and every note wrote all three
sections (48k: 3/3 against 0/3). The largest decode loss at a baseline or input-length
point was 8.3%, llama-benchy's 32 tokens after 4,096 of context and a 2,048-token
prompt. Every first token came sooner except `smoke_hello`'s, 1% later. The deployed env
file was restored.

The failing condition comes from the 70 minutes in which GTT held 1,024 MiB more than
usual and prefill ran at 61–91 t/s. Four of the six agent sessions, wholly or partly, and
the first three documents ran in that state. Outside it:
- the regression items prefilled about three times as fast as the deployed configuration;
- their decode changed by −8% to +61% per point, lower at two llama-benchy points with
  4,096 tokens of context;
- the first `hermes` and `coding` sessions took 405 s and 448 s, against medians of 1,179 s
  and 848 s.

**Not explained.** These are candidate causes, none tested:

1. **VRAM too tight.** With the head at `-ncmoe 36`, VRAM peaked 26 MiB short of full. A
   1 GiB buffer may then have been placed in GTT and stayed there. Prefill would read it
   over PCIe, and the memory clock would fall because VRAM sat idle. The README asks for
   2,048 MiB free; the best-configuration check left 1,822 MiB after its probe.
2. **The card's memory-clock policy alone.** The card runs power profile
   `BOOTUP_DEFAULT`, whose memory-clock row sets no minimum while active. The `COMPUTE`
   profile sets 850 MHz.

Tests that would tell them apart:
- Rerun the workloads item with `dio` and the head at `-ncmoe 37`, about 1.5 GiB more
  free, and watch whether GTT freezes at the higher level.
- While the state lasts, list the card's buffers (`amdgpu_gem_info` in debugfs) to see
  what sits in GTT.
- If the memory clock drops without that GTT state, set the `COMPUTE` profile or pin the
  memory clock and rerun.
