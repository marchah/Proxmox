# Qwen3.8-Flash-Next: the full benchmark batch on CT 123

Plan committed 2026-10-09 · Run not started · Status: planned

## Question

What does CT 123, as it serves today, deliver on all eight DIMM channels, measured by the
repository's endpoint batch (`make bench GPU=2`) rather than the placement probe?

- **Regression items:** single-request baseline, the concurrency sweep, the input-length
  sweep to 32k tokens, and the soak.
- **Workloads:** the scripted agent sessions (`hermes` and `coding`, stopped at 56k on
  the one 64k slot) and document ingestion at 8k, 16k, 32k and 48k tokens.
- **Per phase:** what the card, the CPU and the DIMMs do while it runs.

No full batch has run on GPU 2 before. The batch's only GPU 2 figures, from 2026-10-02
(b11018, four DIMMs), are replaced by this run's.

## What answers it

- Per regression item, the suite's `REPORT.md` and `SLO.md`: prefill and decode rates per
  prompt and depth, time to first token, and request latency per concurrency point. Decode
  is quoted with its prompt class and depth, and prefill separately.
- Agent sessions: per preset, `session_wall_seconds`, the per-band prefill and decode
  rates, and `cache_misses`, which should be zero with nothing else using the server.
- Document ingestion: per prompt size, prefill rate, time to first token and decode rate,
  median of three runs.
- The target telemetry merged into each run: card power, clocks and busy % against the
  250 W cap, GTT, CPU cores in use, and the hottest DIMM, per phase.
- Output: the suite's degenerate-output and error counts per item.
- A run with any DIMM sample at 66 °C is reported as capped, item by item.

## Controls

None. This run is the reference for CT 123's served configuration on eight channels. Its
figures are not compared with the 2026-10-02 run, which used b11018 and four DIMMs.

## Method

Code at the branch head when the run starts; `make bench` stops on uncommitted benchmark
code and records the commit in each run's `versions.json`, with `capture-env.sh`'s
capture. From the repo root on the Mac:

```bash
make bench GPU=2
```

- The batch checks that CT 123 serves its model and has `llamacpp-qwen38fn-reload`, starts
  CT 200 if it is stopped, captures the environment, then reloads CT 123 before each item
  and wraps it with `run-with-target-telemetry.sh`. Afterwards it restores CT 123 at one
  slot and fetches the results.
- Items, in order: `llm-bench-baseline`; `llm-bench-sweep concurrency --points 1 2 4 8 16
  --requests 32`; `llm-bench-sweep input-length --points 128 512 2048 8192 32768
  --output-tokens 32`; `llm-bench-soak`; the workloads profile with
  `BENCHMARK_AGENT_DEPTH=56000`. Repetitions are the suite's own (three runs per workload
  preset and prompt size).
- With one slot, concurrency points above 1 queue behind it; they measure latency under
  queueing, not parallel decode.
- Expected duration: several hours. GPU 2 prefills about 120 t/s and decodes about
  14 t/s at this placement, and the ingestion and session workloads prefill hundreds of
  thousands of tokens. The record gives the actual time.
- Raw data: `pro-v620/results/llamacpp-gpu2/parallel-1/<run>/` on the Mac (gitignored), one
  folder per item.

## Safety

- Every guest the batch does not use stays shut down: CT 120 `llamacpp` (back on GPU 1
  alone after `ct120-cutover.sh to-qwen36`), CT 121 `hermes`, CT 140 `kb-rag`, VM 300
  `docker-host` and CT 201. CT 123 and CT 200 run for the batch. Starting any other guest
  again waits for the owner's go-ahead.
- CT 123 holds only `0000:83:00.0`; CT 120 holds only `0000:03:00.0` and is stopped.
- `gpu-thermal-watchdog` maps `0000:83:00.0` to `123:llamacpp-qwen38fn` and stops it at
  102 °C junction or 101 °C memory; the batch's server runs under that unit.
- The DIMMs have no guard during the batch: the BMC's fan curve is at 100% from 58 °C,
  and the telemetry records the hottest DIMM for each item.
- Keep clear of the Sunday 01:00 backup window.

## Environment

Intended: llama.cpp b11505 (release tarball), Mesa 26.2.4, kernel `7.0.14-22-pve`,
8 × 64 GB DDR4-3200, both V620s at 0 mV and 250 W, CT 123 with 24 cores and 120 GiB on
`0000:83:00.0`. The batch's `versions.json` replaces this paragraph when the run starts.
